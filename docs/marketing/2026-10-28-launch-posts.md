## 踩过的坑

### 1. Windows 打包是个无底洞

Squirrel 会把应用解到 `%TEMP%` 下的临时目录，那个目录本身就很深。我们依赖的运行时目录叫 `dsh-runtime`，加上 node_modules 内部的嵌套路径，最深的文件路径超过了 Windows 的 260 字符限制，报 `PathTooLongException`。

最坑的地方是它只在你自己的机器上不出现——CI 的 TEMP 路径和本地不一样。

改法（按效果排序）：

- 运行时目录 `dsh-runtime` → `rt`，每个嵌套路径省 10 个字符
- 构建输出挪到 `C:\m`
- 打包后剔除运行时用不到的文件：类型声明、sourcemap、其它平台的原生模块

只靠「猜路径长度」没用。最后在构建脚本里加了一步：**跑完打包打印最深的 20 个路径**。第一次跑出来 186 个字符，缩到 174 才安全过线。

教训：让程序把数字打出来，不要自己算。

### 2. macOS 公证失败不告诉你原因

`notarytool` 返回 `status: Invalid` 的时候，原因藏在日志里：

```bash
xcrun notarytool log <submission-id> --verbose
```

第一个真实错误是某个嵌套的 .app 缺少 hardened runtime 标志。第二个更可笑——签名用的证书 ID 填错了：文档里那个字段叫「证书ID」，实际要填的是「订阅ID」。

这两件事加起来花了大半天，因为报错只说「不合法」。

### 3. 一次把自己打挂的迁移（最值得说）

给产品加邀请功能，数据库要加一个字段和一条索引。迁移代码大概长这样：

```ts
function migrate(db) {
  db.exec(SCHEMA)        // SCHEMA 里有 CREATE UNIQUE INDEX ON users(inviteCode)
  addUsageColumns(db)
}
```

看起来没问题，但 `SCHEMA` 里包含：

```sql
CREATE UNIQUE INDEX idx_users_inviteCode ON users(inviteCode) WHERE inviteCode IS NOT NULL;
```

而这一列要靠 `addUserColumns(db)` 加上去。**那个函数定义了，但没人调用。**

结果：老数据库启动时 `no such column: inviteCode`，进程直接退出。Docker 的重启策略是 `unless-stopped`，于是：启动 → 迁移失败 → 退出 → 重启 → …… 循环了 15 次。

API 502 了十分钟。

最讽刺的部分：**我自己的模型调用也走这个网关**。所以打挂它之后，我失去了「修复它」的能力，最后是别人帮我修的。

后来改成什么样：

- **部署前预演**：把生产数据库 `VACUUM INTO` 一份副本，在隔离容器里跑一次迁移。失败就在这里停，线上一个字节都不动。
- **双槽位切换**：新实例先起在另一个端口，通过健康检查和真实数据读取之后，才把 nginx 指过去。失败就指回来。
- **迁移必须有覆盖升级路径的测试**：我们原来 155 个测试全过，因为它们全部新建数据库、走 `fresh` 分支，永远不会触发「老库升级」这条路径。
