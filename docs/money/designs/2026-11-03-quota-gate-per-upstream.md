# 闸门按上游判断：不占免费额度的请求只看钱包

| 项 | 值 |
|---|---|
| 日期 | 2026-11-03 |
| 状态 | **shipped**（修复已实现，待部署） |
| 依赖 | [`standard.md`](../standard.md) 第 4 节「闸门」 |
| 影响 | `server/src/server.ts` 的闸门判断；无 schema 变更 |

## 1. 问题

用户 `F` 在**一分钱没充**的情况下，钱包欠到 **−¥21.96**。

## 2. 根因

`standard.md` 第 57 行写的闸门是：

> 免费剩余 > 0 **或** Wallet 余额 > 0 即放行；两者都耗尽才拒绝。

而 10-24 引入的规则是：**OpenAI 上游的请求不占免费额度**（`paidFromFreeMicro = 0`）。

两者相撞：

```
用户用 Terra（OpenAI）
→ 不消耗免费额度 → freeRemaining 永远满
→ 闸门看到「免费剩余 > 0」→ 永远放行
→ 全部成本记进钱包 → 钱包一路负下去
```

`F` 的 123 次 Terra 调用（¥21.23）全部落在已经为负的钱包上。

## 3. 修复

闸门改为按上游提问：

```ts
const canPay = openaiPath ? credit.walletMicro > 0 : !credit.exhausted
if (settings.quotaMode === 'enforce' && !canPay) { 429 }
```

- **OpenAI 请求**：只看钱包余额，因为免费额度对它无意义
- **其他请求**：保持原判（免费剩余或钱包任一有余额）

`creditState` 本身不动——它表达的「两个桶还剩多少」仍然正确，展示层继续用它。

## 4. 影响面

修复前，近 7 天用过 OpenAI 的账号有 3 个：

| 账号 | 调用 | 结算 | 钱包 |
|---|---:|---:|---:|
| `F` | 123 | ¥21.23 | **−¥21.96** |
| `1906817538` | 2 | ¥0.14 | **−¥0.14** |
| `fengzhe` | 1 | ¥2.46 | +¥18.58 |

前两个会继续恶化，第三个只是因为有余额才没暴露。

## 5. 欠款怎么处理

**不动**。这 ¥22.10 是历史账，已经记在 `wallet_ledger` 里。修复只阻止继续扩大。

用户下次用 OpenAI 时会看到「余额不足」，这正好是让他充值的时机——欠款会在充值后自动抵扣。

## 6. 验证

- 新增测试：钱包为 0 + `quota.mode = enforce` 时，OpenAI 请求返回 429 且**不得到达上游**
- 修改原有测试「免费额度不覆盖 OpenAI」：先充值再验证 `paidFromFreeMicro = 0`（原测试假设「没钱也能用」，那正是 bug）
