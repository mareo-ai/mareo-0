# 恢复 v12 数据库的网关请求

- 日期：2026-11-18
- 状态：confirmed, to implement
- 依赖：`docs/money/standard.md`，`server/src/db.ts`、`quota.ts`、`wallet.ts` 当前实现。
- 影响：网关数据库迁移及受额度检查阻塞的模型请求；不修改金额计算、额度数值或账本记录。

## 目标与范围

生产 `user_version=12` 的 `users` 表缺少 `abuseSince`，当前额度检查查询该列导致模型请求返回 500。将 schema 版本推进至 13，使已有的用户列迁移在旧库启动时执行；补充真实 v12 结构的升级测试。此修复只恢复既有服务，不新增标记账号的操作、不对任何人设置标记，也不改变现有结算、赠送或报表规则。

当前代码包含针对 `abuseSince` 非空账号的额度和赠送限制，但 `standard.md` 未记载该政策。本次迁移不主动设置该字段、不修改相关逻辑；如需启用或调整此政策，应另行完成金额规则设计与审核。

## 计算与边界

结算依赖 `standard.md` 第 2–6 节，不更改算法。测试样例：普通账号免费剩余 0.40 元、钱包 1.00 元，结算 0.60 元时仍先扣免费 0.40 元、钱包扣 0.20 元；末笔透支、微元向上取整继续由现有测试覆盖。v12 老账号新增列为 NULL，不因迁移被标记；保留已有 v12 中非 NULL 标记，不覆盖。升级前后请求、余额、账本行不重算或改写。

## 数据模型与流程

- `users.abuseSince`：当前代码已定义为 nullable TEXT；对缺列的 v12 库执行已有 `ALTER TABLE ... ADD COLUMN`，既有行自动为 NULL。已存在此列的库不重复添加。
- `PRAGMA user_version` 从 12 推进为 13；新库、旧 v1/v11/v12 库均继续使用已有迁移链。无删列、重类型、账本迁移或历史回填。
- 模型调用前：沿用当前额度检查，确保查询字段存在；调用后：沿用原结算与账本事务；赠送：沿用原 `grantCredit`；每日重置沿用北京时间自然日。任何规则变化不在本修复内。

## 接口、客户端与报表

无接口、配置或客户端变更；用户已安装版本继续使用原接口，不需客户端发版。报表口径和输出不变。运营标记入口与人工标记操作均不在本次范围。

## 部署与验证

1. 本文提交并审阅后，修改 `server/src/db.ts` 的 schema 版本及 `server/test/migration.test.ts`，从真实 v12 结构（包括此前新库已有字段及现网缺字段两种情况）测试升级、重复打开、用户/令牌/usage/账本保留，以及普通账号额度检查；运行服务端完整测试。
2. 核对待部署源码与生产当前版本差异，使用 `server/deploy/deploy-gateway.sh` 备份数据库与源码，先以生产库副本演练，再启动空闲槽位、验证、切换流量。不得直接修改生产数据库或使用裸 `docker compose up --build`。
3. 确认生产 schema v13、字段存在、数据库完整性和业务链路；对账本及历史用量做只读核验。真实请求验证若需临时账号或产生调用费用，须遵循相应生产操作权限及审批；不能以健康检查代替业务验证。

## 风险与取舍

- 当前网关 500 会持续至修复上线。已有字段的库与缺字段的库都必须可升级；验证从旧结构开始，不能仅测试新库。
- 部署脚本健康探针未必覆盖额度 SQL；需额外验证该查询及实际请求链路。
- 如现网源码与待部署工作树存在未经审阅的差异，暂停部署，不覆盖其他人的生产改动。生产规则与记录如有冲突，另行解决，不能在本修复中静默调整。
