# Search / Fetch 调用的成本口径（2026-11-01 起）

| | |
|---|---|
| 日期 | 2026-10-21 |
| 状态 | **draft，待评审** |
| 依赖 | [`../standard.md`](../standard.md)（真实成本、毛利、报表的定义） |
| 影响 | 新增一项平台成本的记录与报表口径；**本阶段不改变用户计价** |
| 触发 | [DeepSeek 公告](https://api-docs.deepseek.com/zh-cn/news/news261017/)：Search / Fetch 自 **2026-11-01 00:00（北京时间）** 起按 **¥5 / 千次** 收费；在此之前免费 |

## 1. 目标与边界

**目标**：让这项新成本**可见**，且不破坏现有毛利算术。

**不做**：
- 不向用户按次收费（本阶段由我们吸收）
- 不并入 `actualMicro`（见 §2 的理由）
- 不改搜索供应商、不缓存搜索结果

**为什么现在就要做**：公告明确"在 DeepSeek Harness 中使用 DeepSeek API 时会通过 Server 端工具调用访问 Search/Fetch"，也就是说**我们的用户每次搜索都会产生这笔费用**。近 7 天真实量：**461 次搜索请求**，按 ¥5/千次约 **¥2.31**。当前金额很小，但它是"我们付费、账上看不见"的成本，违反报表必须解释成本的原则。

## 2. 计价算术与边界

- 单价：**¥5 / 1000 次 = 5000 微元 / 次**
- **按调用次数计，不按请求数计**：一次模型请求可能触发多次搜索
- 次数来源：响应里的 `usage.server_tool_use.web_search_requests`（Anthropic 形状）
  - 取不到时，若该请求带 `web_search_20250305` 工具 → **记 1 次**，并标记为估计值
- **失败不计费**：`status != 200` 的请求记 0 次
- **不并入 `actualMicro`**：搜索是平台侧成本，不是这次模型调用的成本。并入会让"真实成本"混入非模型项，进而让"毛利 = 结算 − 真实成本"这条恒等式不再解释得清
- 新增独立列 `searchCostMicro`，报表**单列一行**；毛利率仍以模型成本为分母

**worked example**：一次请求触发 2 次搜索 → `searchCalls = 2`，`searchCostMicro = 10000`（¥0.01）。用户账单不变。

## 3. 数据模型（schema v11 → v12）

```sql
ALTER TABLE usage ADD COLUMN searchCalls INTEGER;        -- 该请求触发的搜索次数
ALTER TABLE usage ADD COLUMN searchCostMicro INTEGER;    -- 折算后的平台成本（微元）
```

- 历史行两列为 `NULL`（那时搜索免费，记 0 与记 NULL 是两件事）
- 新增 `searchCallsEstimated` 不需要：估计值只在报表里按"含 `searchCalls` 但无 `server_tool_use` 字段"的比例体现，等真实字段验证后再决定要不要落列

## 4. 流程

1. 代理完成响应后，从响应尾部解析 `usage.server_tool_use.web_search_requests`
2. 解析不到且请求含搜索工具 → 记 1 次（估计）
3. 失败请求 → 0 次
4. 写 `usage.searchCalls` 与 `searchCostMicro = searchCalls × 5000`
5. 报表汇总，与模型成本分列

## 5. 接口与配置

- 用户侧：**无变化**（不发版、无新接口）
- 运维：`cost-report` 增加「搜索调用」段落（次数、成本、估计占比）
- 无需新配置项：单价是官方固定价，写进 `pricing.ts` 常量即可

## 6. 客户端影响

无。搜索调用发生在服务端到 DeepSeek 之间，客户端不需要任何改动。

## 8. 上线顺序

1. 本文评审通过
2. 实现记录（**不做收费**）：schema v12 + 解析 + 报表
3. **11-01 之后**核对第一次账单：DeepSeek 后台的 Search 费用 vs 我们记录的 `searchCostMicro`，允许 ±5% 偏差（次数口径可能不完全一致）
4. 若偏差大，回看是否漏记（例如 Fetch 与实际 Search 分开计价）

## 9. 验证

- 单测：`server_tool_use` 有值 / 无值兜底 / 失败不计 / 多次搜索相加
- 真实请求：在预发发一次带 `web_search` 的请求，核对记录次数与响应字段
- 账单核对：11-01 后一周内至少对一次账

## 10. 风险

| 风险 | 处置 |
|---|---|
| 次数口径不一致（估计值偏大或偏小） | 报表显示"估计占比"；以官方账单为准，偏差记入文档 |
| Search 与 Fetch 分别计价 | 公告写两者各 ¥5/千次；如合并计价再调系数 |
| 用户量增长后成本变显著 | 量级到了再评估是否转嫁（届时另开文档，改用户计价属另一件事） |
| 免费期结束的突然成本 | 已有记录，报表可见；不需要额外告警 |
