## 1. 目标与范围

**目标**：让用户用微信支付或支付宝**一次性充值**，充值成功后 Mareo Wallet 余额增加；支付系统只负责收钱，Wallet 仍是独立系统，充值只是 Wallet 的一个来源（`source = purchase`）。

**做**：固定三档金额（¥10 / ¥30 / ¥100）、扫码二维码支付、服务端回调确认、主动查单兜底、充值记录、后台充值口径；开发期用模拟 provider 跑通全链路。

**不做**：订阅与自动续费、套餐与折扣、优惠券、充值赠送、自助退款、发票、营销活动、自定义金额（表结构已兼容，第一版界面上不提供）。

**前提**：微信支付商户号与支付宝当面付**都还没办**。因此实现按"provider 可替换"来做：先接 `fake` 实现（与 `rewards` 里的 `fake-ad` 同一套路），资质下来后只换实现，不动订单表与业务逻辑。

## 2. 口径

- **支付成功是唯一依据**：只有服务端验签通过的支付回调，或服务端主动查单得到的"已支付"，才能让订单变成 `paid` 并给钱包入账。客户端显示的"支付成功"不产生任何账务影响。
- **金额换算只在边界**：用户支付的是**分**，钱包记的是**微元**（1 元 = 1e6 微元）。`1 分 = 10 000 微元`，档位金额都必须是 10 000 的整数倍。全程整数，禁止浮点。
- **入账金额 = 用户实付金额**，1:1，不做赠送（将来若做赠送，另记一笔 `promotion`，不改 `purchase`）。
- 入账走唯一入口：`grantCredit(userId, amountMicro, 'purchase', { externalRef: orderId, channel: provider })`。
- Wallet 余额**不过期、不清零**；消费仍是**先每日免费额度、后 Wallet**（见 `standard.md` 第 4 节，本次不改）。
- 单笔上限 ¥500、单日（北京日）上限 ¥2000、二维码有效期 2 小时；这些是风控默认值，都写在服务端，客户端不能改。

## 3. 数据模型（schema v9 → v10）

新增一张表，不动现有表；历史数据无处可迁（充值是全新业务）。

```sql
CREATE TABLE IF NOT EXISTS payment_orders (
  orderId       TEXT PRIMARY KEY,      -- 我们生成的商户订单号，也是 grantCredit 的 externalRef
  userId        TEXT NOT NULL REFERENCES users(id),
  provider      TEXT NOT NULL,         -- wechat | alipay（用户选的渠道）
  amountMicro   INTEGER NOT NULL,      -- 入账金额（微元），服务端按档位决定
  amountFen     INTEGER NOT NULL,      -- 提交给支付平台的金额（分）
  status        TEXT NOT NULL,         -- pending | paid | failed | cancelled | refunded
  transactionId TEXT,                  -- 支付平台流水号（paid 时写入）
  codeUrl       TEXT,                  -- 二维码内容（pending 期间）
  createdAt     TEXT NOT NULL,
  expiresAt     TEXT NOT NULL,
  paidAt        TEXT,
  refundedAt    TEXT,
  rawCallback   TEXT,                  -- 最近一次支付成功回调原文，排障与重放用
  updatedAt     TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_payment_orders_user ON payment_orders(userId, createdAt DESC);
CREATE INDEX IF NOT EXISTS idx_payment_orders_status ON payment_orders(status, expiresAt);
-- 同一笔支付流水只能挂到一个订单：防跨订单重放
CREATE UNIQUE INDEX IF NOT EXISTS idx_payment_orders_txn
  ON payment_orders(provider, transactionId) WHERE transactionId IS NOT NULL;
```

迁移：`SCHEMA_VERSION = 10`，`CREATE TABLE IF NOT EXISTS` + 幂等建索引，与 v9 同样的路子（新库走 `SCHEMA`，老库走 `migrate`）。不需要 `addUsageColumns` 那样补列。

## 4. 关键流程

### 4.1 下单

```
POST /payment/orders { tier: 't10'|'t30'|'t100', provider: 'wechat'|'alipay' }
  → 鉴权（账号 token）
  → tier → amountMicro 由服务端查表得到（客户端传的任何金额一律忽略）
  → 校验：provider 合法、该账号 pending 未过期订单 < 3、当日已入账充值 < ¥2000
  → orderId = 'MR' + yyyyMMddHHmmss + 6 位随机（22 字符，字母数字，满足两家长度与字符集要求）
  → provider.createOrder(...) → { codeUrl, expiresAt }
  → 落库 status='pending'，返回 { orderId, amountMicro, amountFen, qrSvg, expiresAt, status }
```

### 4.2 支付成功回调（唯一的事实来源）

```
POST /payment/notify/wechat   （微信 v3：AES-256-GCM 解密 + 平台公钥验签）
POST /payment/notify/alipay   （支付宝：表单编码 + RSA2 验签）
  → provider.verifyCallback(headers, rawBody)
      验签失败 / 解密失败 → 拒绝（微信 4xx、支付宝返回 'failure'），绝不入账
  → 取出 { orderId, transactionId, amountFen, succeeded }
  → 按 orderId 查订单：不存在 → 拒绝并告警（可能是别人的单/伪造）
  → amountFen ≠ 订单金额 → 拒绝并告警（**不改状态**，留待人工核对）
  → confirmPayment(orderId, { transactionId, amountFen })
  → 回复成功（微信 200 空 body；支付宝纯文本 'success'）
```

### 4.3 confirmPayment —— 唯一能让订单变成已支付并入账的地方

回调、主动查单、人工补单三条路都调它，所以幂等只在这里实现：

```
BEGIN
  UPDATE payment_orders
     SET status='paid', transactionId=?, paidAt=?, rawCallback=?, updatedAt=?
   WHERE orderId=? AND status IN ('pending','cancelled','failed')     -- 注意：cancelled 也要收
  if changes = 0 → 已经是 paid/refunded：说明是重复回调，直接返回 { duplicated: true }，**不入账**
  grantCredit(userId, amountMicro, 'purchase', { externalRef: orderId, channel: provider })
COMMIT
```

两层幂等：**状态机**（只有非 `paid` 才能转 `paid`）+ **账本唯一索引** `(source, externalRef)`。任何一层挡住都不会重复加钱。

`cancelled`/`failed` 也允许转 `paid`：二维码过期不等于收不到钱（用户在有效期内扫码、过期后才付款完成），钱到了就必须认。`paid`/`refunded` 则拒绝——那是重复回调或已冲正的订单。

### 4.4 主动查单兜底（用户体验的关键）

回调可能丢。客户端每次轮询 `GET /payment/orders/:orderId` 时，若订单仍 `pending` 且 `createdAt` 已超过 10 秒，服务端**主动查单**（微信 `GET /v3/pay/transactions/out-trade-no/{orderId}`、支付宝 `alipay.trade.query`），查到已支付就走同一个 `confirmPayment`。同一订单 5 秒内最多查一次，避免刷爆接口。

### 4.5 过期与关单

进程内定时器每 5 分钟：`UPDATE payment_orders SET status='cancelled' WHERE status='pending' AND expiresAt < now`。网关是单进程单实例，用 `setInterval` 就够（不需要外部调度器）。

### 4.6 已支付订单的边界举例（写测试用）

- **¥30 微信支付**：下单 `amountMicro=30_000_000`、`amountFen=3000` → 回调 `amountFen=3000` → `grantCredit(30_000_000, 'purchase', orderId, 'wechat')` → 账本 +¥30.00，`balanceAfter` 与订单一一对应。
- **重复回调 5 次**：第 1 次 `changes=1` 入账；第 2–5 次 `changes=0`，返回 `duplicated`，账本仍只有一行。
- **金额被篡改**：回调 `amountFen=1`（订单是 3000）→ 拒绝，订单保持 `pending`，日志告警，人工用 CLI 核对。
- **验签失败**：签名被改 → 400/'failure'，不入账、不改状态。
- **过期后才支付**：订单已 `cancelled`，回调到达 → 转 `paid` 并入账（钱真的到了）。
- **跨订单重放**：同一 `transactionId` 挂到第二个订单 → 唯一索引拒绝，入账失败并告警（此时第一笔已经入账）。

## 5. 接口与配置

**统一 provider 接口**（`server/src/payment/`）：实现两个文件 + 一个假的：

```ts
interface PaymentProvider {
  readonly channel: 'wechat' | 'alipay'
  createOrder(order: PaymentOrder): Promise<{ codeUrl: string; expiresAt: Date }>
  verifyCallback(headers, rawBody): Promise<{ orderId, transactionId, amountFen, succeeded } | undefined>
  queryOrder(order: PaymentOrder): Promise<'pending' | 'paid' | 'closed' | 'failed'>
}
```

`PAYMENT_MODE=fake|live` 选择实现：`fake` 模式下两个渠道都走模拟实现（订单里的 `provider` 仍如实记录用户选的渠道），因此**数据模型在测试与线上完全一致**。生产若不是 `live`，假回调入口一律 404。

**HTTP 接口**（全部新增，老客户端不受影响；`/quota` 不变）：

| 接口 | 鉴权 | 说明 |
|---|---|---|
| `GET /payment/config` | 账号 | `{ enabled, tiers: [{tier, amountMicro}], channels: ['wechat','alipay'] }`；`enabled=false` 时客户端不显示充值入口（避免"按钮点了没反应"） |
| `POST /payment/orders` | 账号 | 下单，返回二维码 SVG 与订单号 |
| `GET /payment/orders/:orderId` | 账号（只能看自己的） | 查单；`pending` 超过 10 秒会触发主动查单 |
| `GET /payment/orders?limit=20` | 账号 | 充值记录（倒序） |
| `POST /payment/notify/wechat` | 无（验签即鉴权） | 微信 v3 回调 |
| `POST /payment/notify/alipay` | 无（验签即鉴权） | 支付宝异步通知，成功返回纯文本 `success` |
| `POST /payment/fake/notify` | 共享 token，仅 `PAYMENT_MODE=fake` | 开发/测试用，走**与真实回调完全相同**的校验与入账路径 |

**二维码在服务端生成**（新增网关依赖 `qrcode`），接口直接返回 SVG/data-URL。理由：客户端插件是被 `stage-runtime` 包进 `ModuleLoader` 的单文件，加 npm 依赖很别扭；服务端生成还能让整条链路在服务端可测。

**签名/加密的实现方式**：两家都用 `node:crypto` 自实现（微信 v3 的 RSA-SHA256 签名、AES-256-GCM 解密、平台公钥验签；支付宝的 RSA2 签名与验签），**不引入第三方支付 SDK**。理由：协议面很窄（各三四个函数），自实现代码量小、无供应链风险，且资金路径上不放不可控代码；代价是要用固定测试向量把这些函数钉死（见第 9 节）。

**配置（`.env`，与 `DEEPSEEK_API_KEY` 同级，只放服务器）**：

```
PAYMENT_MODE=fake|live
PAYMENT_PUBLIC_BASE_URL=https://api.mareo.cn     # 回调地址前缀
WECHAT_MCHID= / WECHAT_APPID= / WECHAT_API_V3_KEY= / WECHAT_SERIAL_NO= / WECHAT_PRIVATE_KEY_PATH=
ALIPAY_APP_ID= / ALIPAY_PRIVATE_KEY_PATH= / ALIPAY_PUBLIC_KEY_PATH=
PAYMENT_FAKE_TOKEN=            # 仅 fake 模式使用
```

**运营 CLI**（`server/src/payment-cli.ts`，`npm run payment`）：`list [--status] [--day]`、`show <orderId>`、`pay <orderId>`（人工补单，走 confirmPayment）、`cancel <orderId>`；覆盖"用户说付了钱但没到账"的客服场景：按订单号查，必要时人工补单，账本留痕。

## 6. 客户端

入口放在现有 "Account" 设置页（`brand/client.cjs` 已有 `AccountSection`）：显示 `Mareo 余额 ¥x.xx` + `充值` 按钮（`enabled=false` 时不显示）；面板内三档金额、微信/支付宝两个渠道、二维码（`<img>` 直接放服务端给的 SVG）、`等待支付…`、每 2 秒轮询订单状态、到账后提示并刷新余额；下方是最近 20 条充值记录（时间 / 金额 / 渠道 / 状态）。

用户侧**不出现**商户号、交易流水号、费率、回调等实现细节。**需要一次客户端发版**（与额度条两行可以并到同一次）。

## 7. 报表

在现有「钱包与毛利」分节下新增一块「充值订单」，口径写进 `standard.md` 第 7 节：

| 数字 | 定义 |
|---|---|
| 下单数 / 支付成功数 | 当日创建的订单数 / `paid` 的订单数（按 `createdAt` 归属北京日） |
| 支付成功率 | `paid / (paid + failed + cancelled)`，`pending` 不计入分母 |
| 渠道占比 | 当日 `paid` 金额与笔数按 `provider` 分组 |
| 充值人数 | 当日 `paid` 的 distinct `userId` |
| 平均到账时长 | `paidAt − createdAt` 的均值与 P90 |
| pending 积压 | 当前仍 `pending` 且未过期的订单数（该 > 0 就值得看） |

「充值金额」「已消耗额度」「Wallet 余额」沿用现有口径（充值 ≠ 收入、毛利只按已消耗口径）。

## 9. 验证

- **单测**：档位 → 金额换算（三档 × 分/微元边界）、金额不匹配拒绝、签名/解密用**固定测试向量**（自造密钥对，构造合法回调必须通过；改一个字节必须失败）、状态机（`pending→paid` 只入账一次；`cancelled→paid` 允许；`paid→paid` 返回 duplicated；`refunded→paid` 拒绝）、跨订单 `transactionId` 唯一、过期置 cancelled、单日/单笔上限、pending 数量上限。
- **集成**：真实网关 + `fake` provider 跑通"下单 → 回调 → 到账 → 重放 5 次余额不变 → 查单兜底 → 过期取消"，并核对 `payment_orders` 与 `wallet_ledger` 一一对应。
- **真实小额**：`PAYMENT_MODE=live` 后，微信与支付宝各付 ¥10，核对订单 `status/transactionId/paidAt`、账本一行 `purchase`、`/quota` 余额增加；同一回调原文重放一次，余额不变。
- **报表**：用真实数据渲染一次，确认成功率、渠道占比、充值人数与账本自洽。

## 10. 风险与取舍

1. **资质与审核时间不可控**：微信商户号、支付宝当面付签约都可能要几天到两周。已用 `fake` provider 把开发与资质解耦；风险是上线时间取决于资质，不取决于代码。
2. **验签实现错误＝资金安全漏洞**：所以自实现的每个函数都要有固定测试向量（合法必须过、篡改必须拒），并在上线前用真实回调验证。
3. **回调丢失导致"付了没到账"**：三层兜底——主动查单、报表 pending 积压监控、CLI 人工补单（有账本留痕）。
4. **金额单位换算错误**：集中在 `payment/amount.ts` 一个文件，禁止别处做换算；测试覆盖三档。
5. **重复入账**：状态机 + 账本唯一索引双层，且都在同一事务里。
6. **费率与现金流**：支付通道费 0.6% 已含在毛利模型里；钱先进对公账户（T+1 结算），所以"充值 ≠ 收入"在现金流上也成立。
7. **合规**：充值余额属于预收款；隐私政策与用户协议需要补充"充值、余额、退款"条款（第一版不做自助退款，但条款要写清）。发票第一版不做，但要在协议里说明可联系客服。
8. **不做退款的风险**：用户付错金额或要求退款时，第一版只能人工处理（`payment-cli` + 平台后台退款 + 手动调账）；订单表保留 `refunded` 状态与 `refundedAt`，为将来留位。
