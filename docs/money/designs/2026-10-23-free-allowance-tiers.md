# 免费额度分档递减 + Sol 退出免费额度

| 项 | 值 |
|---|---|
| 日期 | 2026-10-23 |
| 状态 | **shipped**（2026-10-23 实现，网关测试 149/149） |
| 依赖 | [`standard.md`](../standard.md) 第 3、4、7 节 |
| 影响 | 网关计费分摊（`quota.ts` / `server.ts` 的 `billingFor`）、运营报表的「额度影响」口径、客户端额度条文案 |

## 1. 目标与范围

**目标**

1. 把「每天固定 ¥10」改成**按账号累计消耗分档递减**的每日额度，重度使用者更快降到 ¥3，轻度使用者长期保持高额度。
2. **Mareo-O-\*（OpenAI 上游）不消耗免费额度**，只扣 Wallet——它们的单价是 DeepSeek 的十几倍，一次请求就吃掉一天额度。

**范围外（本设计不做）**

- 不送首充优惠、不加新充值档位（另行决策）。
- 不改销售倍率、不改长上下文计价、不改账本结构。
- 不做「额度回升」（只降不升，见 §11）。
- 不改客户端的百分比展示（2026-10-23 已上线）。

## 2. 现况

`quota.ts` 每次请求：`freeRemainingMicro = settings.dailyFreeMicro − 当日已用`，`dailyFreeMicro` 是全局固定值（默认 ¥10）。

`usage.paidFromFreeMicro` 已经按笔记录了「这笔请求由免费额度承担了多少结算成本」，索引 `idx_usage_userId_ts(userId, ts)` 支持按账号聚合。

## 3. 规则

### 3.1 当日额度的判定

设 `T` = 该账号**在当日 0 点之前**累计的免费额度消耗（微元）：

```
T = SUM(usage.paidFromFreeMicro) WHERE userId = ? AND ts < startOfDay(now)
```

| `T` | 当日额度 |
|---|---:|
| < ¥30 | ¥10 |
| ¥30 ≤ T < ¥60 | ¥6 |
| ¥60 ≤ T < ¥100 | ¥4 |
| ≥ ¥100 | ¥3 |

**当日额度一旦确定，当天内不再变**——即使当天消耗把 `T` 推过档位边界，明天才降档。这是为了与「第二天刷新才降」的行为一致，也避免当天中途额度突然缩水导致已用超额。

### 3.2 免费额度不覆盖的模型

`provider === 'openai'` 的请求：

```
paidFromFreeMicro = 0
```

全部由 Wallet 承担。Wallet 不足时的行为不变（放行最后一笔、之后 429）。

### 3.3 不变的部分

- 扣减顺序仍是「先免费额度、后 Wallet」（只是 Sol 跳过第一桶）。
- 允许最后一笔透支（`standard.md` 第 4 节）。
- 每日已用金额仍在北京时间 0 点重置。
- 结算倍率、`billableMicro` 的计算完全不变。

## 4. worked examples

**E1 — 重度用户第 4 天降档**

| 天 | 开始时 T | 当日额度 | 当天用了 | 当天结束 T |
|---|---:|---:|---:|---:|
| D1 | ¥0 | ¥10 | ¥9.5 | ¥9.5 |
| D2 | ¥9.5 | ¥10 | ¥10（透支最后一笔） | ¥20 |
| D3 | ¥20 | ¥10 | ¥10 | ¥30.5 |
| D4 | ¥30.5 | **¥6** | ¥6 | ¥36.5 |

**E2 — 轻度用户保持高额度**

每周用一次、每次 ¥2：T 增长 ¥2/周，第 15 周才越过 ¥30。**在此之前一直是 ¥10**。

**E3 — 当天跨档不缩水**

D4 开始时 T = ¥29.9（额度 ¥10），当天一口气用了 ¥12——`T` 变成 ¥41.9，但**当天额度仍是 ¥10**，D5 才降到 ¥6。

**E4 — Sol 不占免费额度**

账号免费额度剩 ¥8、Wallet ¥0。发一次 `gpt-6-sol`：

- 结算 ¥17.76 → `paidFromFreeMicro = 0`，Wallet 需承担 ¥17.76
- Wallet 为 0 → 但「允许最后一笔透支」放行，Wallet 变成 −¥17.76
- 下一次请求：Wallet ≤ 0 且免费额度不覆盖 Sol → **429**

对照：同账号发 `deepseek-flash`，用掉 ¥0.03，仍从免费额度扣，正常工作。

**E5 — 新用户**

T = 0（无历史）→ 当日额度 ¥10。与今天一致。

## 5. 数据模型

**不新增表、不新增列。** `T` 由 `usage.paidFromFreeMicro` 历史聚合得出，是唯一数据源，不会与实际消耗不一致。

代价：每个请求多一次聚合查询。索引 `(userId, ts)` 已覆盖；实测单账号 ≤ 5,000 行，可接受（现有实现每次请求也已经在做当日聚合）。

**历史行**：存量 `paidFromFreeMicro` 直接参与 `T` 的计算——老账号会按「已经白嫖了多少」自动落到相应档位，不需要迁移脚本。

## 6. 流程

**请求前（`server.ts` 的额度闸门）**

1. 算 `T`（`ts < startOfDay(now)`）。
2. 由 `T` 查当日额度 `dailyAllowanceMicro`。
3. `freeRemainingMicro = max(0, dailyAllowanceMicro − 当日已用)`。
4. 判定 `exhausted`：`freeRemainingMicro ≤ 0 && walletMicro ≤ 0`。

**结算后（`billingFor`）**

1. `provider === 'openai'` → `paidFromFreeMicro = 0`。
2. 否则 `paidFromFreeMicro = min(freeRemainingMicro, billableMicro)`（与今天一致）。
3. Wallet 部分照旧。

**配置**

| 键 | 默认 | 说明 |
|---|---|---|
| `quota.freeTiers` | `30000000:6000000,60000000:4000000,100000000:3000000` | `累计阈值:当日额度`，全微元、逗号分隔、阈值严格递增；**最后一档即下限**，不需要单独的 floor 键 |
| `quota.dailyFreeMicro` | `10000000` | **保留**，作为 T 未达任何边界时的额度（¥10），避免破坏既有配置读到该键的地方 |

`config-cli` 写入时校验：阈值必须是正整数且严格递增，额度必须是非负整数；格式不对**直接拒绝**，不会静默存下一个改坏所有人的值。

## 7. 接口

`GET /quota` 的响应结构不变（`free.limitMicro` 现在等于当日额度而非全局值，客户端不需要改）。

**新增一个字段**：`free.coveredProviders`（如 `["deepseek"]`）——让客户端能在模型选择处提示「该模型不消耗免费额度」。

## 8. 客户端影响

- 额度条：不需要改（百分比已上线）。
- **需要加提示**：选到 `Mareo-O-*` 时说明「此模型不消耗每日免费额度，直接扣余额」。否则用户会在额度 100% 的情况下莫名其妙被 429——这是本次改动**最容易被误解**的地方。
- 发版才能生效；网关侧改动可先上（老客户端只是多扣余额，不报错）。

## 9. 报表

`standard.md` 第 7 节的「额度影响（影子估算）」口径不变。新增两行便于观察 rollout：

| 数字 | 定义 |
|---|---|
| 当前额度分档分布 | 按 `T` 把账号分到四档，各档账号数 |
| 免费额度日均成本 | `SUM(actual × paidFromFree / billable)` 按天 |

## 10. 上线顺序

1. 先上配置项与 `T` 的聚合（**不改变行为**：所有档位都配成 ¥10，等价于现状）。
2. 观察一天，确认 `T` 的分布符合预期（老账号落点是否合理）。
3. 打开真实档位，`quota.mode` 保持 `enforce`。
4. Sol 退出免费额度**单独一步**上线（它改变的是「谁能白用」，感知最明显）。

## 11. 风险与取舍

| 风险 | 说明 |
|---|---|
| **重度用户流失** | 14 天数据显示成本集中在每天用满 ¥10 的账号，而这些账号最可能付费。降到 ¥3 会让他们每天可用量砍掉 70%，可能不是充值而是离开 |
| **Sol 彻底失去体验入口** | Sol 不占免费额度后，新用户不充钱就无法试用；而 Sol 恰恰是「惊艳感」最强的模型。建议后续单开「Sol 一次性试用额度」，本设计不做 |
| **老账号突然降档** | 按历史 `T` 计算，部分老账号上线当天就直接落到 ¥3。建议上线前先查一遍分布，必要时对个别账号用 `quota` 配置临时豁免 |
| 只降不升 | 停用回来的用户不会恢复额度。若将来要改，属于口径变更，需再写一份设计 |
| 每次请求多一次聚合 | 单账号行数在万级以内可接受；超过后加缓存或落一列 |

## 12. 验证

- 单元：四档边界（T = ¥29.99 / ¥30 / ¥59.99 / ¥60 / ¥99.99 / ¥100）、当天跨档不缩水、新用户 T = 0。
- 单元：Sol 请求 `paidFromFreeMicro = 0`，且 Wallet 为 0 时被 429；DeepSeek 请求不受影响。
- 集成：用临时账号造出 `T = ¥35` 的历史，确认当天额度是 ¥6，且 `GET /quota` 返回的 `limitMicro` 一致。
- 真实数据：上线前统计现有 65 个账号的 `T` 分布，确认有多少会立刻降到 ¥3。
